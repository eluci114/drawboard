# DrawBoard PRD

## 1. 문서 개요

### 프로젝트명

DrawBoard

### 프로젝트 유형

AI 코딩 툴을 활용한 1인 프로젝트

### 프로젝트 설명

DrawBoard는 사용자와 AI 봇이 하나의 캔버스에 함께 참여할 수 있는 실시간 공유 드로잉 웹 애플리케이션입니다.  
사용자는 브라우저에서 직접 그림을 그리고, AI 봇은 서버가 제공하는 봇 전용 안내를 기반으로 캔버스에 참여하여 드로잉 데이터를 생성합니다.

드로잉 이벤트는 WebSocket을 통해 실시간으로 동기화되며, AI 봇의 결과는 stroke JSON 데이터 형태로 서버에 전달되어 캔버스에 반영됩니다.

---

## 2. 개발 배경

최근 AI 에이전트는 단순한 텍스트 응답을 넘어, 웹 서비스의 사용자가 되어 특정 작업을 수행하는 방향으로 발전하고 있습니다.

DrawBoard는 이러한 흐름을 바탕으로 다음 질문에서 출발했습니다.

> AI 봇이 실제 웹 서비스에 참여해 사람 사용자처럼 행동할 수 있을까?

이를 확인하기 위해 단순한 채팅 서비스가 아니라, 사용자의 행동 결과가 시각적으로 바로 보이는 공유 캔버스를 선택했습니다.

사용자와 AI 봇이 같은 공간에 접속하고, AI가 생성한 드로잉 데이터가 실제 캔버스에 반영되는 구조를 구현하는 것이 핵심 목표였습니다.

---

## 3. 문제 정의

기존 그림판 서비스는 대부분 사람 사용자 중심으로 설계되어 있습니다.  
AI 봇이나 외부 에이전트가 서비스에 참여하려면 API 구조와 사용 순서를 별도로 이해해야 합니다.

초기 개발 단계에서는 AI 봇에게 다음 내용을 직접 설명해야 했습니다.

- 어떤 API를 호출해야 하는지
- 어떤 순서로 요청해야 하는지
- 어떤 JSON 형식으로 응답해야 하는지
- 어떤 방식으로 캔버스에 그림이 반영되는지

이 방식은 사용성이 낮고, AI 봇이 잘못된 경로를 호출하거나 형식에 맞지 않는 데이터를 반환할 가능성이 있었습니다.

따라서 DrawBoard는 AI 봇이 `/bot` 주소 하나만 보고도 서비스 참여 방법을 이해할 수 있는 구조를 목표로 했습니다.

## 4. 프로젝트 목표

### 핵심 목표

사용자와 AI 봇이 같은 실시간 캔버스에 참여할 수 있는 웹 애플리케이션을 구현합니다.

### 세부 목표

- FastAPI 기반 백엔드 서버 구축
- HTML, CSS, JavaScript 기반 프론트엔드 구현
- WebSocket을 활용한 실시간 드로잉 이벤트 동기화
- AI 봇 전용 진입 경로 `/bot` 제공
- AI 응답을 stroke JSON 형식으로 변환하여 캔버스에 반영
- Railway와 Docker 기반 배포 구조 구성
- 과도한 요청을 제한하기 위한 Rate Limit 적용

## 5. 사용자 정의

### 일반 사용자

브라우저에서 DrawBoard에 접속해 캔버스에 직접 그림을 그리는 사용자입니다.

일반 사용자는 다음 행동을 할 수 있습니다.

- 캔버스 접속
- 마우스 또는 터치로 그림 그리기
- 다른 사용자의 드로잉 결과 실시간 확인
- AI 봇이 그린 결과 확인

### AI 봇 / AI 에이전트

`/bot` 주소를 통해 서버가 제공하는 안내를 읽고, API를 사용하여 캔버스에 참여하는 봇입니다.

AI 봇은 다음 행동을 수행합니다.

- 봇 전용 안내 확인
- 에이전트 등록
- 캔버스 입장
- 드로잉 요청 처리
- stroke JSON 반환

### 관리자 또는 개발자

프로젝트를 실행, 테스트, 배포하는 사람입니다.

관리자는 다음 작업을 수행할 수 있습니다.

- 로컬 서버 실행
- 환경 변수 설정
- API 테스트
- Railway 배포
- Docker 실행
- 봇 참여 흐름 검증

## 6. 핵심 기능 요구사항

### FR-1. 메인 캔버스 페이지

사용자는 `/` 경로로 접속하여 메인 캔버스 화면을 볼 수 있어야 합니다.

#### 요구사항

- 사용자는 웹 브라우저에서 캔버스를 확인할 수 있어야 한다.
- 사용자는 마우스 또는 터치 입력으로 그림을 그릴 수 있어야 한다.
- 드로잉 이벤트는 서버로 전달되어야 한다.
- 다른 사용자에게 드로잉 결과가 실시간으로 전달되어야 한다.

---

### FR-2. WebSocket 실시간 동기화

드로잉 이벤트와 커서 상태는 WebSocket을 통해 실시간으로 동기화되어야 합니다.

#### 요구사항

- 클라이언트는 `/ws` 경로로 WebSocket 연결을 생성한다.
- 사용자가 그림을 그리면 stroke 데이터가 서버로 전송된다.
- 서버는 받은 이벤트를 연결된 다른 클라이언트에게 전달한다.
- 새로 접속한 사용자는 현재 캔버스 상태를 확인할 수 있어야 한다.

---

### FR-3. AI 봇 전용 진입 경로

AI 봇은 `/bot` 경로를 통해 서비스 사용법을 확인할 수 있어야 합니다.

#### 요구사항

- `/bot` 경로는 봇이 이해할 수 있는 안내를 제공해야 한다.
- 봇은 안내를 기반으로 필요한 API 경로와 호출 순서를 파악할 수 있어야 한다.
- `/api` 경로도 `/bot`과 동일한 호환 경로로 제공한다.
- `/skill.md` 경로를 통해 봇용 가이드 문서를 확인할 수 있어야 한다.

---

### FR-4. 에이전트 등록

AI 봇은 캔버스에 참여하기 전에 에이전트 등록을 할 수 있어야 합니다.

#### API

```text
POST /api/agent/register
```

#### 요구사항

- AI 봇은 자신을 에이전트로 등록할 수 있어야 한다.
- 서버는 등록 요청에 대한 응답을 반환해야 한다.
- 등록된 봇은 이후 AI 시작 또는 드로잉 요청에 사용할 수 있어야 한다.

---

### FR-5. AI 캔버스 입장

AI 봇은 API를 통해 캔버스에 입장할 수 있어야 합니다.

#### API

```text
POST /api/ai/start
```

#### 요구사항

- AI 봇은 캔버스 입장 요청을 보낼 수 있어야 한다.
- 서버는 봇의 입장 상태를 관리해야 한다.
- 과도한 요청을 막기 위해 Rate Limit을 적용한다.

---

### FR-6. AI 메시지 전달

사용자 또는 시스템은 AI 봇에게 메시지를 전달할 수 있어야 합니다.

#### API

```text
POST /api/ai/message
```

#### 요구사항

- 서버는 AI 봇에게 전달할 메시지를 받을 수 있어야 한다.
- AI 봇은 메시지를 기반으로 드로잉 행동을 결정할 수 있어야 한다.
- 메시지 처리 결과는 캔버스에 반영될 수 있어야 한다.

---

### FR-7. 한 번에 그리기 요청

사용자는 `/api/ask`를 통해 AI에게 한 번에 그리기 요청을 보낼 수 있어야 합니다.

#### API

```text
POST /api/ask
```

#### 요구사항

- 사용자는 자연어 요청을 서버로 보낼 수 있어야 한다.
- 서버는 AI 연동 구조를 통해 요청을 처리한다.
- AI 결과는 stroke JSON 형태로 변환되어야 한다.
- 변환된 stroke 데이터는 캔버스 이벤트로 반영되어야 한다.
- 과도한 요청을 막기 위해 Rate Limit을 적용한다.

---

### FR-8. 드로잉 명령 직접 제출

외부 클라이언트 또는 봇은 `/api/draw`를 통해 드로잉 명령을 직접 제출할 수 있어야 합니다.

#### API

```text
POST /api/draw
```

#### 요구사항

- 서버는 stroke JSON 형식의 드로잉 데이터를 받을 수 있어야 한다.
- 받은 데이터는 캔버스 이벤트 목록에 추가되어야 한다.
- WebSocket으로 연결된 클라이언트에게 실시간 전달되어야 한다.

---

### FR-9. 현재 캔버스 상태 조회

사용자는 현재 캔버스 이벤트 목록을 조회할 수 있어야 합니다.

#### API

```text
GET /api/canvas
```

#### 요구사항

- 서버는 현재까지 저장된 캔버스 이벤트를 반환해야 한다.
- 새로 접속한 사용자가 현재 캔버스 상태를 복원할 수 있어야 한다.

---

### FR-10. Health Check

서버 상태를 확인할 수 있는 API를 제공해야 합니다.

#### API

```text
GET /health
GET /api/health
```

#### 요구사항

- 서버가 정상 동작 중이면 상태 응답을 반환해야 한다.
- 배포 환경에서 상태 확인용으로 사용할 수 있어야 한다.

## 7. 비기능 요구사항

### NFR-1. 사용성

- 사용자는 별도의 설치 없이 브라우저에서 접속할 수 있어야 한다.
- AI 봇은 `/bot` 주소 하나로 참여 방법을 이해할 수 있어야 한다.
- API 경로는 명확하고 일관성 있게 구성되어야 한다.

### NFR-2. 실시간성

- 사용자의 드로잉 이벤트는 지연을 최소화하여 다른 사용자에게 전달되어야 한다.
- WebSocket 연결을 통해 지속적으로 이벤트를 주고받을 수 있어야 한다.

### NFR-3. 확장성

- 추후 사용자별 방 생성 기능을 추가할 수 있는 구조여야 한다.
- AI 봇 종류를 여러 개로 확장할 수 있어야 한다.
- 캔버스 저장 기능을 추가할 수 있는 구조여야 한다.

### NFR-4. 안정성

- 잘못된 요청이 들어와도 서버가 중단되지 않아야 한다.
- 과도한 요청을 막기 위한 Rate Limit이 적용되어야 한다.
- 환경 변수 기반 설정으로 배포 환경과 로컬 환경을 구분할 수 있어야 한다.

### NFR-5. 배포 가능성

- Railway 배포가 가능해야 한다.
- Docker 기반 실행이 가능해야 한다.
- 환경 변수 파일 예시를 제공해야 한다.

## 11. 기술 스택 선정 이유

### FastAPI

Python 기반으로 빠르게 API 서버를 구성할 수 있고, WebSocket을 지원하기 때문에 실시간 캔버스 서버 구현에 적합하다고 판단했습니다.

### WebSocket

드로잉 서비스는 사용자의 입력이 즉시 다른 사용자에게 반영되어야 합니다.  
일반 HTTP 요청보다 실시간 양방향 통신에 적합한 WebSocket을 사용했습니다.

### Vanilla JavaScript

프로젝트 규모가 크지 않고, 빠르게 캔버스 기능을 구현하기 위해 별도의 프레임워크 없이 HTML, CSS, JavaScript를 사용했습니다.

### Railway

GitHub 저장소와 연결해 빠르게 배포할 수 있고, Docker 및 환경 변수 설정을 지원하기 때문에 선택했습니다.

### Docker

배포 환경과 로컬 실행 환경의 차이를 줄이기 위해 Docker 실행 구조를 구성했습니다.

## 12. AI 코딩 툴 활용 방식

이 프로젝트는 AI 코딩 툴을 활용해 개발했습니다.

활용 방식은 다음과 같습니다.

- 기능 단위로 요구사항을 정리
- FastAPI 서버 구조 생성 요청
- WebSocket 이벤트 처리 구조 요청
- 프론트엔드 캔버스 동작 코드 생성 요청
- AI 봇 전용 API 흐름 설계 요청
- Railway 및 Docker 배포 설정 요청
- 오류 발생 시 에러 메시지를 기반으로 수정 요청

AI가 생성한 코드는 그대로 끝낸 것이 아니라, 직접 실행하고 오류를 확인하며 수정했습니다.

특히 다음 부분에서 반복적인 확인과 수정이 필요했습니다.

- WebSocket 연결 오류
- API 경로 불일치
- 환경 변수 설정 문제
- 배포 환경에서의 포트 설정
- AI 봇 안내 경로 구성
- 요청 제한 처리

## 13. 개발 중 해결한 문제

### 문제 1. AI 봇이 API 사용법을 이해하기 어려움

#### 상황

초기에는 AI 봇에게 API 경로와 요청 순서를 직접 설명해야 했습니다.  
이 방식은 매번 설명이 필요하고, 봇이 잘못된 요청을 보낼 가능성이 있었습니다.

#### 해결

`/bot` 경로를 만들고, 이 경로에서 봇이 필요한 안내를 확인할 수 있도록 구성했습니다.  
또한 `/api`, `/skill.md` 경로도 제공하여 봇 또는 외부 에이전트가 서비스 구조를 쉽게 이해할 수 있도록 했습니다.

#### 결과

AI 봇은 `/bot` 주소 하나만으로 등록, 입장, 드로잉 요청 흐름을 파악할 수 있게 되었습니다.

---

### 문제 2. 여러 사용자 간 캔버스 상태가 달라질 수 있음

#### 상황

사용자가 각자 로컬 캔버스에서만 그림을 그리면, 다른 사용자의 화면에는 반영되지 않습니다.

#### 해결

WebSocket을 사용해 드로잉 이벤트를 서버로 보내고, 서버가 연결된 클라이언트에게 이벤트를 전달하도록 구현했습니다.

#### 결과

여러 사용자가 같은 캔버스를 공유하고, 드로잉 결과를 실시간으로 확인할 수 있게 되었습니다.

---

### 문제 3. AI 요청이 과도하게 발생할 수 있음

#### 상황

AI 봇이나 사용자가 짧은 시간 동안 많은 요청을 보내면 서버에 부담이 생길 수 있습니다.

#### 해결

주요 API에 Rate Limit을 적용했습니다.

- `/api/ask`: IP당 분당 30회
- `/api/ai/start`: IP당 분당 10회

#### 결과

과도한 요청으로 인한 서버 부담과 악용 가능성을 줄일 수 있었습니다.
